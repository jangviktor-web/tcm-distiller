# 编码卫生与乱码防治（G8 · nihaixia 实战提炼）

> 定位：通用 TCM skill 编码纪律。nihaixia skill 曾因**繁体残留 + GBK mojibake（U+FFFD / HTML 实体）在多份文档生成后才被发现**，返工成本高。本文件把"防 + 查 + 修"固化，避免重复踩坑。
> 蒸馏器自身的 `## 错误处理机制 → 素材校验` 仅一句"非 UTF-8 自动转码"，不足以覆盖；本文件为执行级补充。

## 一、铁律（G8）

- **统一简体 UTF-8**：所有产出文件（SKILL.md / modules/ / references/ / cases/）一律简体中文 + UTF-8 无 BOM。
- **零乱码 / 零繁体残留**：这是注册的隐性门槛，也是人物口吻还原的前置条件（繁体混简体破坏阅读连贯）。

## 二、预防（生成期）

1. **源头统一**：收录原文若来自繁体版（如台版医籍、倪海厦讲稿），先用 `opencc -c t2s` **一次性全量转简体**再进入蒸馏流程，不要边蒸馏边转。
2. **转码校验**：素材入仓前跑 `file -i` / Python `chardet` 确认 UTF-8；非 UTF-8 先转码再读，避免子 Agent 在错误编码上"安静产出"。
3. **脚本输出**：所有生成/清洗脚本（Python）显式 `encoding='utf-8'`，写文件不漏参。
4. **命名 kebab-case**：文件名一律 `NN-english-kebab.ext`（见坑位百科"中文文件名"坑），中文只进内容不进文件名，规避跨平台编码歧义。

## 三、排查（交付前必做）

按 nihaixia 实测优先级，**三级扫描**：

| 优先级 | 类型 | 特征 | 工具 |
|--------|------|------|------|
| P0 | **U+FFFD 替换符** | `�` 乱码块，最显眼但最易被忽视 | `grep -nP '\x{FFFD}' file` 或 Python 遍历 |
| P1 | **HTML 实体残留** | `敍/厦/纪/术` 等 GBK 字节被误读为 HTML 实体后的错字 | 已知实体映射表逐字核对 |
| P2 | **异写 / 笔误** | `娴→懒`、`戲碼/娴熟` 等被误报为 mojibake 的正常字（**注意假阳性**：不要无脑替换，先确认是否真乱码） | 人工 + 上下文判定 |

**全量扫描脚本**（参考）：
```bash
# 遍历 skill 目录找三类问题
for f in $(find skills/{name} -name '*.md'); do
  grep -nP '\x{FFFD}' "$f" && echo "  ^FFFD in $f"
  grep -nE '敍|厦|纪|术' "$f"    # 已知实体残留候选
done
```

## 四、修复（发现后）

- **U+FFFD**：回源文件取正确字替换；源也无则标 `[缺失]` 不臆造。
- **HTML 实体**：按映射表（`敍→叙`、`厦→厦`、`纪→纪`、`术→术` 等）定点替换。
- **繁体残留**：`opencc -c t2s` 整目录重转（已转过的简体文件不会二次变化，可安全重跑）。
- **假阳性防护**：`戲碼`、`娴熟` 等是正常词，**不要**当 mojibake 改；改前用 `grep -n` 看上下文确认。

## 五、达尔文验证（nihaixia 实证）

- 达尔文 paired 测试参与"繁→简"转换与 mojibake 修复的质量判定：转换后全量扫描 **0 个 U+FFFD + 0 个 HTML 实体残留** 才算通过。
- 教训：**乱码不能等"后来才发现"**——必须作为 Phase 3 / Pipeline B 注册前的**硬性健康检查项**（与索引失效扫描同级）。

## 六、接入点

- Pipeline A：Phase 1 源码入仓即跑"预防"1-2；Phase 3 注册前跑"排查"三级扫描。
- Pipeline B：每轮优化改动后，重跑三级扫描（改动常引入新异写）。
- 错误处理章"素材校验"条目升级为指向本文件。
